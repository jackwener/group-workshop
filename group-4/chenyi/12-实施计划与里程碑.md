## 1. 里程碑（S1～S4）

> **切分原则**：每刀切出一个**可演示的用户价值**。不是"接口写好了"，而是"能给业务看什么"。

**示例 — S1**：

**S1 会话管理**：创建/列表/删除会话 API + 前端会话侧栏 → 满足 REQ-001 部分 → 验证 TC-M01-020～025

| 阶段 | 交付要点（可演示） | 满足的 REQ/US | 验证 TC |
|------|-------------------|---------------|---------|
| **S1** 会话管理 | 会话 CRUD API（`POST /sessions`、`GET /sessions`、`DELETE /sessions/<id>`）+ 前端侧栏（新建、列表、删除、选中切换） | REQ-M1QA-001 | TC-M01-020～025 |
| **S2** 问答核心 | 问答提交 API（`POST /ask`）+ 三级降级编排 + 前端输入区与回答卡片渲染（含来源标签、引用折叠） | REQ-M1QA-002 | TC-M01-001～010 |
| **S3** 历史与状态 | 问答历史记录读取（`GET /sessions/<id>/records`）+ 前端三态渲染（空态/欢迎态/对话态）+ 健康检查接口（`GET /capabilities`）+ Header 能力芯片 | REQ-M1QA-003、REQ-M1QA-004 | TC-M01-030～040 |
| **S4** 发布准备 | 种子数据填充（≥ 10 条）+ 全链路 E2E 测试通过 + Demo 模式验收 + 文档与部署说明完善 | 全部 REQ | TC-M01-全集 |

## 2. WBS 任务拆分

> **拆分原则**：按**工程职责**切（路由、存储、Agent、前端），不按功能切。一个 W 可跨多个 S 迭代推进。

| 任务ID | 任务名称 | 具体内容 | DoD（指向 Spec） | 推进阶段 |
|--------|----------|----------|------------------|----------|
| W1 | 路由实现 | `agent_bp.py` 6 个端点注册、参数校验、traceId 注入、HTTP 状态码、错误响应格式 | 对齐 `09` 全部端点契约与错误码清单；Route 层不含业务逻辑 | S1 起贯穿 S4 |
| W2 | 存储层 | `storage.py` JSON 文件 CRUD、软删除、`query_count` 自增、首次问答自动命名、文件损坏兜底 | 对齐 `10` §3～§6 数据模型与方法清单；Storage 层不调用外部 API | S1～S2 |
| W3 | Agent 编排 | `agent.py` 三级降级链（CoPaw → 百炼 → Demo）、`answer_source` 标识、超时控制（4500ms/级）、降级 WARNING 日志 | 对齐 `07` §1.2 降级策略；`08` §4 三级降级编排；Agent 层不感知 HTTP | S2 |
| W4 | 前端视图 | React 组件树（Header / Sidebar / MainContent / InputArea）、三态渲染、回答卡片、引用折叠、能力芯片、错误 toast | 对齐 `06` §1～§7 全部功能规格；使用 `fetch` API，不引入 axios | S1～S3 |
| W5 | 状态机 | 前端 8 个 `useState` 变量管理、`useEffect` 数据加载时机、提交 loading 态、会话切换联动刷新记录 | 对齐 `06` §7 状态管理表；确保刷新页面后历史数据完整恢复 | S2～S3 |
| W6 | 测试门禁 | pytest 单元测试（Storage / Agent / Route 分层）、fixtures 种子数据、P0 用例优先覆盖、E2E 主路径脚本 | 对齐 `13` 测试策略；P0 用例全通过方可合并至主分支 | S1 fixture，S2 P0，S3～S4 全集 |

| WBS \ 阶段 | S1 | S2 | S3 | S4 |

| **W1** 路由 | ● sessions CRUD 端点 | ● ask 端点 | ● records + health 端点 | ○ 边界修复 |
| **W2** 存储 | ● sessions JSON CRUD + 软删除 | ● 记录落库 + query_count 自增 | ○ 兜底逻辑补全 | — |
| **W3** Agent | — | ● 三级降级链 + 超时控制 | ○ 降级日志完善 | ○ Demo 种子优化 |

## 5. 依赖与风险

**依赖链**：

**S1 会话管理**（Storage + 路由 + 前端侧栏就位）→ **S2 问答核心**（必须先有 session_id 才能提问）→ **S3 历史与状态**（必须先有问答记录才能展示历史）→ **S4 发布准备**（全链路通过才能收口）

| 风险 | 影响 | 应对 |
|------|------|------|
| 外部 LLM（CoPaw / 百炼）在开发阶段不可用 | S2 问答核心无法真实联调 | W3 优先实现 Demo 模式，S2 演示以 Demo 兜底；LLM 可用后补测真实链路 |
| PDF 解析库兼容性问题（研报格式多样） | 研报结构化提取准确率不达标，影响 S2 质量 | S2 阶段先以纯文本问答验收核心链路；PDF 解析作为 S3 增量补入，不阻塞 S2 演示 |
| 前端状态管理复杂度超预期（会话切换与记录联动） | S3 三态渲染出现数据错位或闪烁 | W5 在 S2 阶段提前搭好状态骨架，S3 只做增量填充，不做重构 |
