> **本文只做一件事**：按用户能理解的子场景拆成多条 **User Story**，并为每条写清 **REQ-ID**、**验收标准（AC）**。

## 字段说明 — 每条 UserStory 必须包含以下字段

| 字段 | 填写说明 | 数据来源 ← | 流向下游 → |
|------|----------|------------|-----------|
| **需求编号** | 唯一编号，如 REQ-M1QA-001 | ← `02` 采集编号 | → `14` 追踪矩阵首列 |
| **故事** | 作为【角色】，我希望【行为】，以便【价值】 | ← `04` PRD 场景拆解 | → `06` FSD 功能点 |
| **优先级** | P0（必须）/ P1（应该）/ P2（可选） | ← `03` §4 成功标准 | → `12` 里程碑排期 |
| **来源** | 对应 03/04 哪一条需求 | ← `03` 范围 · `04` 场景 | |
| **前置条件** | 触发该故事的前提状态 | ← `04` 用户流程 | → `13` 测试前置 |
| **功能对齐** | 对应功能规格 + 非功能约束 | | → `06` FSD · `07` NFR |
| **设计对齐** | 对应架构、接口、数据、安全 | | → `08` 架构 · `09` API · `10` Data · `11` 安全 |
| **验证对齐** | 对应测试用例 + 追踪矩阵行 | | → `13` TC · `14` 追踪矩阵行 |
| **验收标准** | AC，每条可独立验证 | ← 故事 + `07` NFR | → `13` 测试用例依据 |

## US-001（P0）会话管理

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-001 |
| **故事** | 作为一个用户，我希望能够创建、查看和删除对话会话，以便将不同主题或任务的对话分开管理，保持信息清晰有序。 |
| **优先级** | P0 |
| **来源** | ← 03 §3 核心功能范围 / 04 §3 核心业务场景 |
| **前置条件** | 用户已成功登录系统 |
| **功能对齐** | → 06 §3 Sidebar 会话管理 · 07 §5 数据约束 |
| **设计对齐** | → 08 §前端架构 · 09 GET/POST/DELETE /sessions API · 10 sessions 表 · 11 §会话数据访问控制 |
| **验证对齐** | → 13 TC-001 · 14 第1行 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-001-01 | 创建会话：在会话列表页点击"新建会话"，输入会话名称（如"项目A讨论"）后，系统成功创建并跳转到该会话的空白聊天界面 |
| AC-001-02 | 查看会话列表：在首页或侧边栏，用户能清晰看到所有自己创建的会话列表，包含会话名称和最后活动时间，并可按时间排序 |
| AC-001-03 | 删除会话：在会话列表中选择一个会话并点击"删除"，经二次确认后，该会话及其所有历史消息被永久删除，并从列表中消失 |

## US-002（P0）问答提交

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-002 |
| **故事** | 作为一个用户，我希望在会话中通过自然语言提问并得到回答，以便快速获取信息、解决问题或完成特定任务。 |
| **优先级** | P0 |
| **来源** | ← 03 §3 核心价值提案 / 04 §3 核心业务场景 SC-01 |
| **前置条件** | 用户已进入一个有效的会话上下文 |
| **功能对齐** | → 06 §4 Main 内容区 · 06 §5 输入区域 · 07 §1 性能需求 |
| **设计对齐** | → 08 §服务编排 · 09 POST /sessions/{id}/messages API · 10 messages 表 · 11 §输入输出内容安全检查 |
| **验证对齐** | → 13 TC-002 · 14 第2行 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-002-01 | 正常问答：在会话中输入问题（如"总结一下刚才讨论的要点"），系统在 3秒内 返回一个连贯、相关的文本回答 |
| AC-002-02 | 服务降级：当主问答服务（如外部大模型API）不可用时，系统能无缝切换至备用回答模式，并明确告知用户当前为降级模式 |
| AC-002-03 | 空输入/无效输入处理：用户提交空问题或仅包含特殊字符的问题时，系统给出友好提示（如"您似乎还没有输入问题"），而不会报错或崩溃 |
| AC-002-04 | 流式响应：系统以流式方式（SSE）逐步返回回答内容，用户无需等待完整响应即可看到部分内容 |

## US-003（P0）历史记录

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-003 |
| **故事** | 作为一个用户，我希望能够查看和搜索某个会话内的完整历史对话，以便回顾之前的讨论、引用重要信息或进行知识沉淀。 |
| **优先级** | P0 |
| **来源** | ← 03 §3 可追溯性需求 / 04 §3 核心业务场景 |
| **前置条件** | 目标会话中至少存在一条历史问答记录 |
| **功能对齐** | → 06 §4 Main 内容区 · 07 §1 性能需求 |
| **设计对齐** | → 08 §数据存储设计 · 09 GET /sessions/{id}/messages API · 10 messages 表 · 11 §历史数据隐私保护 |
| **验证对齐** | → 13 TC-003 · 14 第3行 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-003-01 | 查看完整历史：进入任一会话，聊天界面能按时间顺序加载并展示该会话下的所有历史问答记录（用户问题和系统回答交替显示） |
| AC-003-02 | 历史记录搜索：在会话内提供搜索框，输入关键词（如"预算"）后，能高亮显示并定位到包含该关键词的历史消息 |
| AC-003-03 | 数据持久性：用户刷新页面或重新登录后，所有会话的历史记录保持不变，能够完整恢复 |

## US-004（P1）系统健康检查

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-004 |
| **故事** | 作为系统管理员，我希望能够便捷地检查系统各核心组件的运行状态，以便及时发现故障、快速定位问题，保障服务稳定运行。 |
| **优先级** | P1 |
| **来源** | ← 03 §3 系统监控 / 04 §3 核心业务场景 |
| **前置条件** | 系统已完成部署并正在运行 |
| **功能对齐** | → 06 §2 Header 区域 · 07 §2 可用性需求 |
| **设计对齐** | → 08 §监控架构 · 09 GET /api/health API · 10 system_logs 表 · 11 §监控接口访问权限 |
| **验证对齐** | → 13 TC-004 · 14 第4行 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-004-01 | 手动检查：访问系统健康检查端点（如 /api/health），能返回包含数据库连接、核心外部服务（如LLM）状态、磁盘空间等关键指标的JSON状态报告，且状态为"healthy" |
| AC-004-02 | 自动告警：当任何一项核心健康检查失败时，系统能在 1分钟 内通过预设的告警渠道（如邮件、Slack）向管理员发送告警通知，通知中包含具体的失败服务名称和错误码 |
| AC-004-03 | 前端状态展示：在界面 Header 或管理后台的仪表板上，能以可视化形式（如红绿灯状态指示器）清晰展示当前系统的整体健康状态和各个组件的状态详情 |
