> **本文只做一件事**：按用户能理解的子场景拆成多条 **User Story**，并为每条写清 **REQ-ID**、**验收标准（AC）**。（由产品经理用）

## 字段说明 — 每条 UserStory 必须包含以下字段

| 字段 | 填写说明 | 数据来源 ← | 流向下游 → |
|------|----------|------------|-----------|
| **需求编号** | 唯一编号，如 REQ-M1QA-001 | ← `02` 采集编号 | → `14` 追踪矩阵首列 |
| **故事** | 作为【角色】，我希望【行为】，以便【价值】 | ← `04` PRD 场景拆解 | → `06` FSD 功能点 |
| **优先级** | P0（必须）/ P1（应该）/ P2（可选） | ← `03` §4 成功标准 | → `12` 里程碑排期 |
| **来源** | 对应 03/04 哪一条需求 | ← `03` 范围 · `04` 场景 | |
| **前置条件** | 触发该故事的前提状态 | ← `04` 用户流程 | → `13` 测试前置 |
| **功能对齐** | 对应功能规格 + 非功能约束 | | → `06` FSD · `07` NFR |
| **设计对齐** | 对应架构、接口、数据、安全 | | → `08` 架构 · `09` API · `10` Data · `11` 安全 |
| **验证对齐** | 对应测试用例 + 追踪矩阵行 | | → `13` TC · `14` 追踪矩阵行 |
| **验收标准** | AC，每条可独立验证 | ← 故事 + `07` NFR | → `13` 测试用例依据 |

## US-001（P0）会话管理

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-001 |
| **故事** | 作为高级分析师，我希望通过使用AI会话功能，以便提升研报研读效率 |
| **优先级** | P0 |
| **来源** | ← 03 §2 / 04 §2  通过AI提交研究需求 |
| **前置条件** | 用户已登录且有权限访问进入页面 |
| **功能对齐** | → 06 §1 · 07 §1  界面类似豆包助手，左侧有一个会话列表，一个新建会话按钮，点击出现新对话 |
| **设计对齐** | → 08 §1 · 09 SessionAPI · 10 Session表 · 11 §1  参照南方设计规范文档 |
| **验证对齐** | → 13 TC-001 · 14 第1行 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-001-01 | 有权限用户进入后能点击新会话，能出来一个空白会话页，会话列表会新增一条 |
| AC-001-02 | 用户打开首页，会话列表按时间降序展示，最近的在最上面 |
| AC-001-03 | 用户右键列表中一条数据 可以出现删除按键，点击删除，二次确认后删除 |

## US-004（P1）健康检查

| 字段 | 内容 |
|------|------|
| **需求编号** | REQ-M1QA-004 |
| **故事** | 作为运维人员，我希望通过健康检查接口查看系统各组件状态，以便及时发现并处理服务异常 |
| **优先级** | P1 |
| **来源** | ← 03 §5 风险应对 / 04 §5 能力优先级 |
| **前置条件** | 系统已部署，Flask 服务正在运行 |
| **功能对齐** | → 06 §2 Header 能力状态芯片 · 07 §2 可用性需求 |
| **设计对齐** | → 08 §4 三级降级 · 09 HealthAPI · 10 — · 11 §6 审计日志 |
| **验证对齐** | → 13 TC-M01-052～055 · 14 第4行 |

| 验收标准 | 描述（每条可独立测试） |
|----------|----------------------|
| AC-004-01 | 调用 GET /health 返回 200，响应包含 status、timestamp、components、uptime_seconds 字段 |
| AC-004-02 | components 中包含 llm_service、file_storage、database 三个子组件状态，每个含 status 字段 |
| AC-004-03 | LLM 服务不可用时，llm_service.status 返回 degraded 或 unhealthy，整体 status 同步变化 |
