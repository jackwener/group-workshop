# 生成立项提案与范围说明

## 概述

本技能指导 Agent 基于已有的产品需求素材（用户访谈、PRD 草稿、需求采集记录等），生成符合 Spec 文档体系的 `03-立项提案与范围说明.md`。

该文档在六阶段流程中处于 **Proposal 阶段**，回答"为什么要做？"，通过后进入 `04 PRD`。

## 输入要求

Agent 需要从以下来源获取信息（至少一项）：

1. **用户访谈/需求采集记录**（`02` 文档或用户口述）
2. **已有的 PRD 或需求草稿**（`04` 文档）
3. **用户直接描述的项目背景和需求**

如果信息不足，主动向用户追问以下要素：
- 项目要解决什么问题？（痛点）
- 目标用户是谁？
- 技术栈选型？
- 有哪些已知风险？

## 生成流程

### Step 1: 提取痛点

从输入素材中提取 **至少 3 条用户痛点**，每条包含：
- 痛点描述（一句话，格式：`名词短语：具体描述`）
- 来源（用户访谈 / 竞品分析 / 数据分析）

### Step 2: 撰写提案概要

将痛点转化为正面解决方案，用 3-5 句话概括：
- 格式："在 XXX 应用/平台内交付 YYY 能力"
- 要素：核心功能点 + 关键技术能力 + 用户价值

### Step 3: 定义范围边界

明确"做"与"不做"，各 **至少 3 条**：
- "做"：具体的功能模块或能力
- "不做"：明确排除的范围，避免范围蔓延

### Step 4: 制定成功标准

写 **3-4 条可量化的验收标准**：
- 句式：`用户在 X 分钟内完成 XXX 全链路`
- 句式：`未配置 XXX 时系统返回 XXX`
- 每条必须可测量、可验证

### Step 5: 识别风险

列出 **2-3 个主要风险**，每条包含：
- 风险描述
- 影响范围
- 应对策略（降级/兜底/替代方案）

### Step 6: 列出前置条件

定义 Go/No-Go 清单（3-4 条），格式为 checkbox：
- `☐ 条件描述`

## 写作规范

1. **规范词使用**：遵循 RFC 风格 — MUST / SHOULD / MAY / MUST NOT
2. **痛点格式**：`名词短语：具体描述`（如 "信息分散：研报、新闻、数据分布在多个系统"）
3. **成功标准**：必须可量化，含具体数字或明确的判断条件
4. **范围边界**：做/不做要对称，不做项要具体，不能写成模糊限制
5. **风险应对**：必须有具体降级或兜底方案，不能只写"待定"
6. **追溯关系**：文档通过后，痛点应映射到 `04` PRD 的目标，范围映射到 `04` 的能力优先级

## 质量检查

生成后自检以下项目：

- [ ] 痛点 ≥ 3 条，且每条有明确来源
- [ ] 提案概要 3-5 句话，包含核心功能和用户价值
- [ ] 范围内/外各 ≥ 3 条
- [ ] 成功标准 ≥ 3 条，全部可量化
- [ ] 风险 ≥ 2 条，每条有应对策略
- [ ] 前置条件 ≥ 3 条
- [ ] 元数据表格完整（模块编号、名称、技术栈）
- [ ] 日期已填写为当前日期
