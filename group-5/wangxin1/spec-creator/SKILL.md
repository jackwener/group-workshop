# Spec Creator — 需求规格文档生成器

## 概述

基于 14 份文档的 Spec 框架，根据用户需求自动生成完整的项目规格文档集。遵循六阶段流程：

```
Proposal(03-04) → Spec(05-06-07) → Design(08-09-10-11) → Plan(12) → Test(13) → Trace(14)
  Why              What              How             When/Who     OK?      All linked?
```

## 前置准备

### 1. 收集需求信息

生成 Spec 前必须向用户确认以下信息（缺失项主动追问）：

| 必须信息 | 说明 | 示例 |
|---------|------|------|
| **模块编号** | 唯一模块标识 | `M1-IRA` |
| **模块名称** | 中文+英文 | `投研问答助手（Investment Research Assistant）` |
| **技术栈** | 前后端+存储+测试 | `Flask + React + Vite + JSON + pytest` |
| **痛点/背景** | 至少 2-3 条用户痛点 | 信息分散、效率低 |
| **核心功能** | 3-5 项要做的功能 | 会话管理、问答、历史记录 |
| **不做的事** | 3-4 项明确排除的功能 | 多租户、权限管理 |

### 2. 确认模板目录

检查用户工作区是否存在 `spec-template/` 目录。如有，以其为模板基准；如无，使用本 skill 内置的文档结构。

### 3. 确认输出目录

默认输出到 `spec/` 目录。向用户确认输出路径。

## 生成流程

### 四轮螺旋推进（非线性，而是渐进明细）

| 轮次 | 生成文档 | 做什么 | 清晰度 |
|------|---------|--------|--------|
| **1. 起点** | 01 → 02 → 03 → 04 | 总则+采集+立项+PRD | 30% |
| **2. 锚定** | 05 + 09 | 用户故事与API接口互相校准 | 60% |
| **3. 展开** | 08 + 10 → 06 + 07 + 11 | 架构+数据+功能+NFR+安全 | 85% |
| **4. 收口** | 12 + 13 → 14 | 计划+测试+追踪矩阵 | 95% |

**关键原则**：后续文档必须引用前序文档的编号（如 05 引用 03 §3、04 §3）。

## 各文档生成规则

### 01 — Spec 写作总则与文档编号索引

- 填写模块编号、模块名称
- 保留编号体系（00-14）不变
- 更新术语表中项目特有缩写
- 更新源码目录参考（若有代码）

### 02 — 需求来源与采集记录

- 至少包含 2-3 个需求来源（会议纪要 S-01、邮件 S-02、用户访谈 S-03）
- 每个来源必须有：时间、参会人/发件人、痛点/问题、行动项
- 痛点标注优先级 P0/P1

### 03 — 立项提案与范围说明

- §1 背景与问题：从 02 提取 2-4 条痛点，标注来源
- §2 提案概要：3-5 句话，包含核心能力、降级策略、可追溯性
- §3 范围边界：做/不做各 3-5 条
- §4 成功标准：3-4 条可度量指标
- §5 风险：2-3 条，含影响+应对
- §6 前置条件：3-4 条 Go/No-Go checklist

### 04 — 产品需求说明（PRD）

- §1 愿景目标：03 痛点 → 正面目标映射
- §2 目标用户：角色+使用目标+频率
- §3 核心场景：SC-01 ~ SC-05，每条含用户路径
- §4 产品规则：R-01 ~ R-05，含字段约束、降级策略、状态管理
- §5 能力优先级：按 P0/P1 排列，关联场景
- §6 验收标准：可度量，含演示条件
- §7 与05关系：场景→US、规则→AC、优先级映射

### 05 — 用户故事与验收标准

每条 US 必须包含完整字段表：

```
| 字段 | 内容 |
|------|------|
| 需求编号 | REQ-{模块编号}-NNN |
| 故事 | 作为【角色】，我希望【行为】，以便【价值】 |
| 优先级 | P0/P1/P2 |
| 来源 | ← 03 §X / 04 §X |
| 前置条件 | 具体前提状态 |
| 功能对齐 | → 06 §X · 07 §X |
| 设计对齐 | → 08 §X · 09 X API · 10 X表 · 11 §X |
| 验证对齐 | → 13 TC-X · 14 第X行 |
```

AC 规则：
- 每条 AC 必须可独立测试
- AC 编号格式：AC-{US编号}-{序号}，如 AC-001-01
- P0 US 至少 3 条 AC，P1 至少 2 条

末尾附需求追溯总索引表。

### 06 — 功能规格说明（FSD）

- §1 页面布局：ASCII 或描述性布局图
- §2-§5 各区域功能行为：触发→API调用→行为
- §6 错误处理：后端error.code → 前端展示映射
- §7 状态管理：State变量+类型+初始值+用途
- §8 US→FSD 对齐表

### 07 — 非功能需求与约束

- §1 性能：延迟SLO、降级策略
- §2 可用性：服务可用性目标、MTTR
- §3 可观测性：traceId格式、错误码体系
- §4 安全：认证、CORS、速率限制、敏感数据保护
- §5 数据约束：输入约束（长度、必填）、类型约束（枚举值）
- §6 兼容性：Python/Node/框架版本要求

### 08 — 系统架构与技术选型

- §1 架构总览：系统上下文图（ASCII）+ 架构风格决策表
- §2 后端分层：每层允许做/禁止做
- §3 前端架构：UI框架+构建工具+状态管理
- §4 降级编排：链路图+每级provider配置
- §5 数据存储架构：存储演进路线
- §6 部署架构：服务+端口+启动命令
- §7 ADR：至少 2-3 条架构决策记录
- §8 安全架构：当前措施 vs 生产改进

### 09 — API 接口规格（契约真源）

**核心规则**：所有 API 字段名在 09 冻结，其他文档只引用不另起别名。

每个端点必须包含：
- 请求体：字段+类型+必填+约束+说明
- 成功响应：字段+类型+必有+说明
- 示例请求/响应 JSON
- 参数校验规则汇总表
- 完整错误码清单

### 10 — 数据模型与存储规格

- §1 概念模型：实体关系图（ASCII）
- §2 存储引擎选型
- §3-§4 每个实体：字段+类型+必填+约束+说明
- §5 Storage 方法清单：签名+行为+关联TC
- §6 关键业务逻辑（如首次问答自动命名）
- §7 API 响应 DTO 与存储字段映射

### 11 — 安全设计规格

- §1 安全目标与合规
- §2 认证授权：机制+角色权限矩阵
- §3 数据安全：分类分级+加密策略
- §4 接口安全：输入校验、XSS/CSRF/SQL注入防护
- §5 LLM/AI 安全：数据外泄防护、Prompt注入防护
- §6 审计日志
- §7 STRIDE 威胁清单
- §8 部署安全 checklist

### 12 — 实施计划与里程碑

- §1 里程碑 S1-S4：每阶段可演示交付物+关联 REQ+验证 TC
- §2 WBS 任务拆分：按工程职责切（路由/存储/Agent/前端/测试）
- §3 S×W 矩阵：● 主要推进 / ○ 少量涉及 / — 不涉及
- §4 REQ→S→W→TC 总对应表
- §5 依赖与风险

### 13 — 测试策略与质量门禁

- 测试分层：L1 Unit / L2 Integration / L3 Contract / L4 E2E
- 用例拆分原则：正常路径/错误码/分支路径/类型约束 各计 1 条
- TC 编号格式：TC-{模块}-{NNN}
- 每条 TC 必须关联 REQ 编号
- 质量门禁：G-LINT / G-UNIT / G-INT / G-AC / G-PERF
- 追溯关系汇总：REQ → TC 映射

### 14 — 需求追踪矩阵

- §2 需求定义表：每条需求的编号+名称+优先级+来源+详细说明
- §3 正向追溯：需求 → US → API → TC，标注覆盖状态 ✅/❌
- §4 反向追溯：TC → 需求，断言要点
- §5 API端点 → TC 映射：确保每个端点至少 1 条 TC
- §6 覆盖率分析：端点/需求/TC 各维度百分比

## 文档格式规范

### 元数据头（每页必填）

```markdown
# NN — 文档标题

---

| 项 | 值 |
|---|---|
| 模块编号 | {模块编号} |
| 模块名称 | {模块名称} |
| 文档版本 | v0.1 |
| 阶段 | {对应阶段} |
| 上游 | `NN` 上游文档 |
| 下游 | → `NN` 下游文档 |

---
```

### 版本尾（每页必有）

```markdown
---

| 版本 | 日期 | 说明 |
|------|------|------|
| v0.1 | {当前日期} | 首版填写 |
```

### RFC 规范词

| 词 | 含义 |
|----|------|
| **MUST** | 必须，违反即缺陷 |
| **SHOULD** | 建议，不满足需说明理由 |
| **MAY** | 可选 |
| **MUST NOT** | 严禁 |

### 编号规范

- 需求编号：`REQ-{模块编号}-NNN`
- 测试用例：`TC-{模块}-NNN`
- 场景：`SC-NN`
- 产品规则：`R-NN`
- AC：`AC-{US编号}-{序号}`
- ADR：`ADR-NNN`

## 质量检查清单

生成全部文档后，执行以下检查：

- [ ] 05 每条 P0 US 在 14 有映射
- [ ] 14 每条 REQ 在 13 存在至少 1 个 TC
- [ ] 09 每个端点有示例请求/响应/错误体
- [ ] 10 每个实体有字段约束说明
- [ ] 所有 MUST 条目可被测试或监控验证
- [ ] 所有跨文档引用编号一致（如 05 引用 03 §3 → 03 确实有 §3）
- [ ] 09 字段名全局唯一，其他文档只引用不另起别名
- [ ] 时间格式统一 ISO-8601 UTC

## 使用示例

用户说：`帮我根据以下需求生成 Spec 文档：我要做一个XXX系统`

执行步骤：
1. 追问缺失的必要信息（模块编号、技术栈、核心功能等）
2. 确认输出目录
3. 按四轮螺旋顺序生成 01-14 共 14 份文档
4. 执行质量检查清单
5. 输出总结报告
